## Phase Goal

Uit `.planning/ROADMAP.md`, Phase 3, letterlijk:

> Als een trainer ziek is, ziet de beheerder binnen een minuut welke lessen dat raakt en hangt
> hij er een vervanger aan die dat uur écht kan.

Als gebruikersverhaal: **als** beheerder **wil ik** bij een zieke trainer in één werklijst zien
welke lessen dat raakt en er een vervanger aan hangen die dat uur écht kan, **zodat** geen
enkele les stil zonder trainer blijft staan.

<objective>
De ziekmeldingentabel als tekst onderaan `supabase-schema.sql`: `sick_leaves`, een index, en
twee admin-only RLS-policies in de vorm van `rates_write`.

Purpose: dit is de enige plek waar de beheerdersgrens op ziekmeldingen echt bestaat. De grens in
de app (`isAdmin` op het scherm) is netheid; Postgres is de bewaker. En de vorm van die policies
is niet vrij te kiezen: dit project is al twee keer stilzwijgend geraakt door de upsert-val
(`.planning/codebase/CONCERNS.md`) — de app schrijft met een upsert, Postgres toetst de
`with check` ook bij een látere wijziging, en alles wat over de máker van een rij geëist wordt
geldt dus ook voor iedere volgende beheerder die de rij aanpast. Vandaar `is_admin()` op beide
zijden en géén `created_by`.

**Claude draait geen SQL en maakt geen verbinding met Supabase.** De dev-server wijst naar de
échte productiedatabank van de club. Dit plan schrijft uitsluitend tekst in een bestand; de
gebruiker draait de migratie zelf in plan 08 (D-14).

Output: één blok onderaan `supabase-schema.sql`. Verder niets.
</objective>

       blijft bestaan.
    3. De upsert-val: alleen de beheerder ziet en beheert deze tabel, dezelfde grens als
       `coach_rates` en `lesson_groups`, en om dezelfde reden géén `created_by`-kolom of

       keer stilzwijgend door geraakt.

    De tabel zelf: `create table if not exists sick_leaves` met `id text primary key`,
    `coach_id text not null references users(id) on delete cascade`, `van date not null`,
    `tot date not null`, `reden text`, `created_at timestamptz not null default now()`,
    `retracted_at timestamptz`.

    Zet bij `on delete cascade` een eigen commentaarregel die het verschil met
    `lesson_groups.coach_id` (dat `on delete set null` gebruikt) verklaart: een ziekmelding heeft
    geen betekenis meer zodra zijn trainer weg is, terwijl een les moet blijven bestaan en
    terugvalt op "de vaste trainer gaf hem zelf". Dat verschil is bewust en hoort in het bestand
    te staan, anders wordt het later "rechtgetrokken".

    Daarna `create index if not exists sick_leaves_coach_idx on sick_leaves (coach_id);`,
    `alter table sick_leaves enable row level security;`, en twee policies, elk voorafgegaan door
    een `drop policy if exists`: `sick_leaves_select` voor `select` `to authenticated using
    (is_admin())`, en `sick_leaves_write` voor `all` `to authenticated using (is_admin()) with

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| app → Postgres (`sick_leaves`) | Elke gebruiker van de app praat met dezelfde tabel via dezelfde anon key. RLS is de enige echte scheiding tussen een beheerder en een trainer. |
| beheerder A → beheerder B (upsert) | De app schrijft met een upsert; een `insert` van gebruiker A wordt later een `update` door gebruiker B. Postgres toetst de `with check` bij allebei. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-07 | Elevation of Privilege | `sick_leaves_write` | mitigate | `is_admin()` op zowel `using` als `with check`, geen `created_by`. Een trainer kan zichzelf of een collega niet ziek melden of een ziekmelding intrekken (D-12). |
| T-03-08 | Information Disclosure | `sick_leaves_select` | mitigate | `is_admin()` op `select`: een ziekmelding draagt een reden — gezondheidsinformatie over een collega. Geen enkele niet-beheerder leest deze tabel. Met de hand nagelopen in plan 08, stap 4. |
| T-03-09 | Tampering | de upsert-val | mitigate | Dit is de val die dit project al twee keer stil raakte. De policyvorm van `rates_write` (geen eigenaarschapscontrole) is de mitigatie; het commentaar in het bestand is de mitigatie tegen het opnieuw introduceren ervan; plan 08 stap 1-3 is de handmatige bevestiging. |
| T-03-10 | Denial of Service | herdraaibaarheid van het schema | mitigate | Een niet-idempotent blok breekt het hele script voor elke volgende migratie. Taak 2 loopt dat expliciet na. |
| T-03-11 | Tampering | de productiedatabank van de club | mitigate | Geen enkele taak in dit plan voert SQL uit of legt een verbinding. De dev-server wijst naar de échte club-databank; een "even testen" zou de agenda van de club wijzigen. Vastgelegd in `<action>` en in de acceptatiecriteria. |
| T-03-SC | Tampering | npm/pip/cargo installs | accept | Deze fase installeert geen enkel pakket — RESEARCH.md, "Package Legitimacy Audit": niet van toepassing. |
